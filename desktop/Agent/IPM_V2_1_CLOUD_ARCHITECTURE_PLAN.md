# IPM v2.1 云端协作架构计划

> **目标**：在 v2 本地工作空间与 KnowClaw Agent 工作流基础上，设计 v2.1 的云端协作能力：外部存储接入、项目/案件多人维护、企业管理与分发、Skill 市场、外部 Agent 记录导入。
>
> **核心原则**：IPM Cloud 不是实时网盘，也不是把 Git 原样搬进法律项目管理软件；它应是一个 **本地优先、显式同步、隐私优先、轻量版本化** 的项目/案件协作层。
>
> **范围**：本文档是 v2.1 云端架构蓝图，覆盖产品边界、数据模型、同步模型、冲突策略、版本存储、外部连接器、企业管理、Skill 市场和阶段路线图。具体接口、数据库表、服务端部署方案在后续实现计划中拆分。

---

## 0. 阅读与维护说明

- 本文档记录 v2.1 云端能力的产品与架构假设，后续需求变更先更新 §1 和 §2，再细化到对应阶段。
- 阶段编号使用 **C0-C8**（Cloud）；每阶段首行保留 `Status:`，便于后续落地时跟踪。
- 本计划默认承接 v2 已完成能力：
  - 本地三域工作区：项目 / 案件 / 学习；
  - 本地文件结构与 `meta/structure.json`；
  - AI 暂存区、文件分类、知识库；
  - KnowClaw 工作空间、文件树、Skill、悬浮窗；
  - 本地 SQLite 与 `userfile` 数据根。
- 本计划不要求一次性实现所有云端能力，v2.1 MVP 应优先验证“本地项目发布到云端、成员拉取副本、显式提交、基础回溯”。

## 1. v2.1 产品边界

### 1.1 v2 与 v2.1 的关系

v2 的核心是：

```text
本地工作空间 + KnowClaw Agent + 文件/知识/Skill 工作流
```

v2.1 的核心应升级为：

```text
本地工作空间 + 云端项目协作层 + 企业策略 + 外部生态连接
```

换句话说，v2.1 不应推翻 v2 的本地优先架构，而是在其上增加云端协作能力。

### 1.2 明确要做

| 方向 | 说明 |
|------|------|
| 外部存储接入 | 微盘、飞书、NAS 等作为外部资料源或项目附件源 |
| 云端项目/案件协作 | 多人维护同一个项目或案件，但以本地副本 + 显式同步为主 |
| 企业管理与分发 | 组织、成员、License、默认模型、模板、策略、Skill 分发 |
| Skill 市场 | 官方/第三方/企业私有 Skill 的安装、更新、启用与审核 |
| 外部 Agent 记录导入 | Kimi Code、Cursor、Claude Code 等会话或工作记录导入 IPM |
| 轻量版本回溯 | 支持误删、误覆盖、误移动后的恢复 |

### 1.3 明确不做

| 不做 | 原因 |
|------|------|
| 不做实时网盘式同步 | 法律项目文件大、离线需求强、静默覆盖风险高 |
| 不做多人在线编辑 Word/PDF/PPT | 与 IPM 定位不符，实现成本高，冲突风险大 |
| 不做 Git 式复杂分支/rebase/merge UI | 普通法律用户不应理解程序员工作流 |
| 不默认上传 KnowClaw 对话与工具调用 | 隐私优先，避免把 AI 思考过程云端化 |
| 不默认标记某文件为 AI 生成 | 云端只把文件视为普通用户提交文件 |
| 不做文件内部 diff 作为 MVP | 大多数文件是二进制文档，逐行 diff 不符合场景 |

## 2. 核心架构判断

### 2.1 本地优先，而不是云端实时中心化

IPM 的项目/案件资料具备以下特点：

- 文件通常较大：PDF、扫描件、图片、PPT、Excel、视频、证据包；
- 多数协作是阶段性提交与审阅，不是同一文件实时多人编辑；
- 对可追溯性要求高；
- 对隐私与离线可用性要求高；
- AI 会在本地工作空间内生成、移动、读取文件。

因此 v2.1 应采用：

```text
本地完整或半完整副本
    ↓ 显式提交
云端项目仓库
    ↓ 显式拉取
其他成员本地副本
```

用户心智应是：

- “我把本地项目发布到团队空间”；
- “我同步团队最新版本”；
- “我提交这次整理成果”；
- “我恢复上一个版本”。

而不是：

- “我保存了一个文件，云端立即覆盖所有人”；
- “我打开文件前必须先从云盘下载”。

### 2.2 借鉴 Git 的思想，但不用 Git 的复杂体验

可借鉴：

| Git 思想 | IPM 产品化表达 |
|----------|----------------|
| clone | 加入项目 / 下载到本地 |
| pull | 同步最新版本 |
| commit | 提交更改 |
| push | 上传更改 |
| branch | 创建个人工作副本 / 方案版本（后续可选） |
| conflict | 有同名或版本冲突需要确认 |
| log | 项目操作记录 / 版本历史 |

不应暴露：

- rebase；
- cherry-pick；
- detached HEAD；
- 手动解决文本冲突；
- commit hash；
- remote/ref 等 Git 术语。

### 2.3 云端不是 AI 过程记录仓库

云端协作项目中，默认不保存：

- KnowClaw prompt；
- KnowClaw response；
- thinking 内容；
- 工具调用参数与结果；
- 使用了哪个模型或 Skill；
- 子任务执行过程；
- “文件是否由 AI 生成”的系统标签。

如果 KnowClaw 在协作项目工作空间内生成了一个文件，云端只将其视为：

```text
用户提交的普通文件
```

是否在文件名、目录、备注中标注“AI 草稿”或“KnowClaw 生成”，由用户自行决定。

## 3. 总体架构

### 3.1 逻辑分层

```text
┌────────────────────────────────────────────┐
│ IPM Desktop                                │
│ - 本地工作空间                              │
│ - 文件管理 / 知识库 / KnowClaw              │
│ - 云端同步 UI                               │
└───────────────────────┬────────────────────┘
                        │
                        ▼
┌────────────────────────────────────────────┐
│ Cloud Sync Client                          │
│ - 变更扫描                                  │
│ - 提交 manifest                             │
│ - 拉取远端 manifest                         │
│ - 冲突命名与本地应用                         │
│ - 大文件上传/下载/缓存                       │
└───────────────────────┬────────────────────┘
                        │
                        ▼
┌────────────────────────────────────────────┐
│ IPM Cloud Services                         │
│ - Workspace Metadata Service                │
│ - Object Storage Service                    │
│ - Version Manifest Service                  │
│ - Collaboration / Audit Service             │
│ - Org Admin / Policy Service                │
│ - Skill Registry Service                    │
│ - Connector Service                         │
└────────────────────────────────────────────┘
```

### 3.2 本地工作空间抽象

v2 当前工作空间可理解为：

```text
workspace = 本地目录 + meta/structure.json + project.db + KnowClaw sessions
```

v2.1 中协作工作空间应升级为：

```text
cloud workspace =
  local working copy
  + cloud workspace binding
  + sync manifest
  + member / permission metadata
  + optional external storage adapters
```

建议在本地工作空间增加云端绑定元数据，例如：

```text
meta/cloud.json
```

示例字段：

```json
{
  "cloudWorkspaceId": "cw_xxx",
  "orgId": "org_xxx",
  "domain": "cases",
  "lastSyncedVersionId": "ver_xxx",
  "syncMode": "manual",
  "largeFilePolicy": "on-demand",
  "createdAt": "2026-06-03T00:00:00.000Z"
}
```

### 3.3 云端服务边界

| 服务 | 职责 |
|------|------|
| Workspace Metadata Service | 项目/案件名称、目录结构、成员、状态、标签 |
| Object Storage Service | 文件 blob、hash 去重、大文件分块、下载 URL |
| Version Manifest Service | 提交记录、版本清单、单文件恢复、项目快照 |
| Collaboration / Audit Service | 文件级操作记录、成员行为审计、冲突事件 |
| Org Admin / Policy Service | 企业成员、License、策略、默认配置 |
| Skill Registry Service | Skill 包、版本、审核、安装、企业私有市场 |
| Connector Service | 飞书、微盘、NAS 等外部数据源接入 |
| Import Service | 外部 Agent 记录导入与结构化归档 |

## 4. 云端应该存什么

### 4.1 默认保存

| 类型 | 是否保存 | 说明 |
|------|----------|------|
| 工作区基础信息 | 是 | 名称、类型、状态、成员、权限 |
| 目录结构 | 是 | 业务目录树、文件夹描述、系统目录标记 |
| 文件对象 | 是 | 用户明确提交或上传的文件 |
| 版本 manifest | 是 | 某版本下路径到文件 hash 的映射 |
| 协作事件 | 是 | 上传、移动、重命名、删除、恢复、提交 |
| 冲突事件 | 是 | 同名文件保留双方版本的记录 |
| 企业策略 | 是 | 模型配置、Skill 配置、保留策略等 |

### 4.2 默认不保存

| 类型 | 默认不保存原因 |
|------|----------------|
| KnowClaw 对话全文 | 隐私风险高，非协作必要数据 |
| prompt / response / thinking | 属于用户本地 AI 工作过程 |
| 工具调用参数与输出 | 可能包含敏感材料路径或内容 |
| AI 生成标签 | 云端不判断文件来源 |
| 本地临时文件 | 不属于用户明确提交成果 |
| 未提交的 AI 暂存建议 | 属于本地工作流状态 |

### 4.3 可选保存

部分团队可能需要更强审计能力，企业版可通过策略开启：

- 提交说明；
- 文件级操作人和时间；
- 文件来源备注；
- 项目级活动流；
- 重要版本归档说明；
- 用户主动生成的工作报告。

注意：即使企业版开启审计，也应避免默认保存 KnowClaw 的完整对话过程。

## 5. 同步模型

### 5.1 基本流程

```text
本地变更扫描
    ↓
生成待提交清单
    ↓
用户确认提交说明
    ↓
上传新增/变更 blob
    ↓
上传版本 manifest
    ↓
云端生成新版本
    ↓
其他成员显式拉取
```

### 5.2 加入云端项目

成员加入项目时应支持三种模式：

| 模式 | 说明 | 适用场景 |
|------|------|----------|
| 完整下载 | 下载全部文件到本地 | 小项目、离线办公 |
| 索引优先 | 只下载目录结构、manifest、小文件 | 大型案件 |
| 按需下载 | 大文件显示占位符，点击后下载 | PDF/视频/证据包较多 |

本地 UI 可显示：

- 已在本地；
- 云端可用；
- 下载中；
- 本地已修改；
- 与云端存在同名版本。

### 5.3 提交粒度

MVP 提交粒度建议为：

```text
一次提交 = 一组文件变更 + 一份目录/元数据变更 + 一个提交说明
```

不要求用户逐个文件写说明，但需要在提交页展示：

- 新增文件；
- 修改文件；
- 删除文件；
- 移动/重命名文件；
- 目录结构变化；
- 可能冲突的同名文件。

### 5.4 拉取策略

拉取云端版本时：

1. 下载远端 manifest；
2. 与本地 `lastSyncedVersionId` 之后的本地变更对比；
3. 可自动应用无冲突变更；
4. 同名且 hash 不同的文件按冲突命名策略保留双方；
5. 删除类操作进入待确认或回收区，不直接物理删除本地文件。

## 6. 简化冲突模型

### 6.1 冲突定义

IPM 不采用程序员 Git 的“同一文本文件不同代码行冲突”模型。

v2.1 MVP 中冲突主要定义为：

```text
同一目录 + 同一文件名 + hash 不同
```

其他可能冲突：

- 本地删除了文件，云端有人修改了同一路径文件；
- 本地移动了文件，云端同一路径新增了同名文件；
- 两人创建了同名文件夹；
- 两人修改了同一文件夹描述。

### 6.2 文件冲突处理

默认策略：

```text
不覆盖，不强制合并，自动保留双方版本
```

示例：

```text
法律意见书.docx
法律意见书（张三版本 2026-06-03 10-20）.docx
```

或：

```text
法律意见书.docx
法律意见书（冲突副本-张三-20260603-1020）.docx
```

用户后续可以：

- 打开对比；
- 重命名；
- 删除其中一个；
- 移动到“历史版本”或“待确认”目录；
- 标记其中一个为正式版本。

### 6.3 目录与元数据冲突

| 场景 | MVP 策略 |
|------|----------|
| 两人新增不同文件夹 | 都保留 |
| 两人新增同名文件夹 | 视为同一文件夹 |
| 文件夹描述冲突 | 后提交覆盖，旧描述进入历史事件 |
| 一人删除文件夹，另一人新增文件 | 不自动删除，进入待确认 |
| 项目状态冲突 | 后提交覆盖，保留事件 |

### 6.4 不做文件内部 diff

MVP 不对以下文件做内部 diff：

- doc/docx；
- pdf；
- ppt/pptx；
- xls/xlsx；
- 图片；
- 视频；
- zip/rar；
- 扫描件。

后续增强可以考虑：

- Word 文档版本对比；
- PDF 页级对比；
- Excel sheet 差异摘要；
- KnowClaw 辅助总结两个版本差异。

但这些应作为增强功能，不是协作底座前置条件。

## 7. 轻量版本控制与存储策略

### 7.1 为什么仍需要版本控制

即使不做完整 Git，IPM 仍应提供版本回溯，原因：

- 用户可能误删文件；
- 用户可能误覆盖正式稿；
- AI 或人工可能移动错目录；
- 团队需要知道某次提交改了什么；
- 律师项目需要保留阶段性成果。

### 7.2 为什么不能粗暴全量快照

法律项目可能包含：

- 大量 PDF；
- 扫描图片；
- 大型 PPT；
- Excel 附件；
- 视频证据；
- 压缩包。

如果每次提交复制完整项目，会导致：

```text
5GB 项目 × 10 次提交 = 50GB 存储
```

这不可接受。

### 7.3 推荐模型：blob 去重 + manifest 快照

文件内容按 hash 存储：

```text
blob = sha256 + size + mime + storageKey
```

版本只保存清单：

```text
manifest:
  /过程文档/法律意见书.docx -> sha256:aaa
  /收到资料/合同.pdf -> sha256:bbb
  /交付成果/汇报.pptx -> sha256:ccc
```

如果文件内容未变，多个版本指向同一个 hash，不重复存储 blob。

### 7.4 大文件版本保留策略

建议按文件大小和类型设置默认保留规则：

| 文件类型/大小 | 默认历史保留 |
|---------------|--------------|
| 小文本/Markdown/元数据 | 最近 30 个版本 |
| Word/Excel/PPT/PDF | 最近 10 个版本 |
| 大型 PDF / 压缩包 | 最近 3 个版本 |
| 视频 / 超大文件 | 当前版本 + 最近 1 个版本 |
| 标记为归档版本 | 长期保留，受企业策略限制 |

企业管理员可配置：

- 项目空间配额；
- 历史版本保留天数；
- 大文件版本数量；
- 归档版本数量；
- 回收站清理周期。

### 7.5 删除与垃圾回收

删除流程：

```text
用户删除
    ↓
当前版本不可见
    ↓
进入回收/历史引用
    ↓
超过保留期
    ↓
检查无任何 manifest 引用
    ↓
物理删除 blob
```

不能简单删除 blob，因为其他版本或其他项目可能仍引用同一个 hash。

### 7.6 MVP 回溯能力

v2.1 MVP 建议支持：

- 项目版本列表；
- 查看某次提交改了哪些文件；
- 恢复单个文件到上一版本；
- 下载某个历史版本文件；
- 恢复目录结构到某次提交；
- 显示项目当前空间占用与历史版本占用。

暂不做：

- 分支；
- rebase；
- 文件内部三方合并；
- 永久完整历史；
- 所有历史大文件无限保存。

## 8. 外部存储连接器

### 8.1 连接器定位

微盘、飞书、NAS 不应都被强行抽象成“实时同步网盘”。在 IPM 中它们应作为：

```text
外部资料源 / 外部项目附件源 / 外部归档目标
```

用户可以从这些来源导入资料、建立引用、拉取更新，必要时将 IPM 成果发布回外部系统。

### 8.2 统一 Connector Adapter

建议定义统一接口：

```text
ConnectorAdapter:
  authenticate()
  list(path)
  stat(fileId)
  download(fileId)
  upload(path, blob)
  move(fileId, targetPath)
  rename(fileId, newName)
  delete(fileId)
  getDelta(cursor)
  getShareLink(fileId)
```

不同厂商实现不同 adapter：

| 来源 | 重点 |
|------|------|
| NAS / SMB / WebDAV | 本地网络路径、权限继承、断线恢复 |
| 飞书云文档/云空间 | OAuth、租户权限、文件 ID、预览链接 |
| 微盘 | 企业文件空间、部门权限、批量下载 |
| 本地附属文件夹 | 现有 `localFolders` 能力升级 |

### 8.3 NAS 优先级

NAS/共享盘可能是最容易落地的第一类：

- 与现有本地附属导入接近；
- 不必先做 OAuth；
- 可通过路径扫描和 hash 建索引；
- 适合律所内部文件服务器。

但需要注意：

- Windows 路径与网络盘符；
- 离线状态；
- 文件锁；
- 权限失败；
- 扫描性能；
- 路径重命名检测。

### 8.4 飞书/微盘优先级

飞书/微盘更适合第二阶段：

- 需要 OAuth / 企业授权；
- 需要处理租户、空间、文件 ID；
- API 限流与分页；
- 需要增量同步 cursor；
- 权限模型与 IPM 权限映射更复杂。

## 9. 企业管理与分发

### 9.1 类 Workbuddy 企业版能力

v2.1 企业版可包含：

| 模块 | 能力 |
|------|------|
| 组织管理 | 企业、团队、成员、角色 |
| License | 席位、到期时间、用量 |
| 项目权限 | 项目成员、只读、编辑、管理员 |
| 模型配置 | 统一 API Key、模型白名单、默认 thinking 等级 |
| Skill 分发 | 默认 Skill、禁用 Skill、企业私有 Skill |
| 项目模板 | 默认目录模板、分类规则模板 |
| 审计日志 | 文件级操作、成员登录、同步记录 |
| 数据策略 | 存储配额、版本保留、回收站保留 |
| 安全策略 | 是否允许外部连接器、是否允许本地导出 |

### 9.2 策略覆盖关系

建议配置优先级：

```text
企业强制策略
  > 团队策略
  > 项目策略
  > 用户本地偏好
```

例如：

- 企业禁止某模型，用户设置不可绕过；
- 企业下发默认 Skill，用户可以启用/禁用非强制 Skill；
- 项目模板由团队设定，但用户仍可在本地新增业务文件夹；
- 企业要求保留 180 天审计日志，本地不能关闭。

### 9.3 桌面端呈现

桌面端需要在设置页显示：

- 当前登录组织；
- 当前 License 状态；
- 哪些配置由企业管理；
- 当前项目是否云端协作项目；
- 同步状态；
- 存储配额。

## 10. Skill 市场

### 10.1 市场目标

v2 已有本地 Skill 管理。v2.1 的 Skill 市场应解决：

- 用户不知道有哪些可用 Skill；
- 团队无法统一分发 Skill；
- Skill 缺少版本、作者、依赖、安全说明；
- 外部开发者无法发布专业工作流。

### 10.2 Skill 包规范

建议 Skill 包包含：

```text
skill.json
SKILL.md
scripts/
assets/
examples/
README.md
```

`skill.json` 示例：

```json
{
  "id": "legal-opinion-draft",
  "name": "法律意见书草拟",
  "version": "1.0.0",
  "author": "IPM",
  "description": "根据案情材料和类案参考生成法律意见书草稿",
  "categories": ["legal", "drafting"],
  "permissions": ["read_workspace", "write_workspace"],
  "dependencies": [],
  "entry": "SKILL.md"
}
```

### 10.3 市场类型

| 类型 | 说明 |
|------|------|
| 官方市场 | IPM 官方发布和审核 |
| 第三方市场 | 外部开发者提交，需审核 |
| 企业私有市场 | 企业内部 Skill，只对组织成员可见 |
| 工作空间 Skill | 项目内 `.knowclaw/skills/`，仅当前项目可用 |

### 10.4 安全原则

- 默认展示 Skill 需要哪些权限；
- 脚本型 Skill 必须提示风险；
- 企业可禁用未审核 Skill；
- Skill 更新应有版本变更说明；
- 允许锁定版本，避免自动升级影响交付流程。

## 11. 外部 Agent 记录导入

### 11.1 目标

支持把 Kimi Code、Cursor、Claude Code 等其他 Agent 的记录导入 IPM，用于：

- 项目复盘；
- 知识沉淀；
- 会话归档；
- 迁移到 KnowClaw 继续处理；
- 提取文件变更和结论。

### 11.2 导入后不等于 KnowClaw 原生会话

外部 Agent 的数据结构差异很大，MVP 不应强行还原为 KnowClaw JSONL。

建议先导入为：

```text
外部工作记录 External Agent Record
```

可进入：

- 知识库；
- 项目活动记录；
- Markdown 归档；
- 可选转换为 KnowClaw 上下文摘要。

### 11.3 标准化字段

```json
{
  "source": "kimi-code",
  "title": "案件材料整理",
  "createdAt": "2026-06-03T00:00:00.000Z",
  "participants": ["user", "agent"],
  "summary": "...",
  "messages": [],
  "artifacts": [],
  "fileChanges": [],
  "tags": ["imported", "agent-record"]
}
```

### 11.4 隐私策略

外部 Agent 记录导入默认保存在本地。

只有用户明确选择“提交到云端项目知识库”时，才进入云端协作项目。

## 13. MVP 建议

v2.1 第一阶段 MVP 建议只做：

1. 云端账户与组织基础；
2. 本地项目发布到云端；
3. 成员加入并拉取副本；
4. 显式提交 / 拉取；
5. blob hash 去重；
6. manifest 版本快照；
7. 简化同名冲突；
8. 单文件恢复上一版本；
9. 基础项目成员权限。

暂缓：

1. 飞书/微盘；
2. Skill 市场；
3. 外部 Agent 导入；
4. 企业复杂审计；
5. 分支/方案版本；
6. 文件内部 diff；
7. KnowClaw 对话云同步。

这样可以优先验证最核心问题：

```text
IPM 的本地项目/案件能否被安全地多人协作维护？
```

## 14. 关键风险

| 风险 | 说明 | 缓解 |
|------|------|------|
| 存储成本失控 | 大文件多版本可能快速膨胀 | hash 去重、保留策略、配额、GC |
| 用户误解为实时网盘 | 期望保存后别人立即看到 | UI 明确“提交/拉取”模型 |
| 冲突体验复杂 | Git 式冲突用户难理解 | 自动保留双方版本，不做强制合并 |
| 隐私风险 | AI 对话/工具调用上云敏感 | 默认不上云，只同步用户提交文件 |
| 外部连接器复杂 | 飞书/微盘权限和 API 差异大 | NAS 优先，云厂商后置 |
| 企业策略侵入本地体验 | 用户偏好与企业策略冲突 | 明确策略优先级和 UI 提示 |
| 离线状态不清晰 | 本地变更与云端版本可能分叉 | 同步状态、lastSyncedVersionId、待提交清单 |

## 16. 当前结论

IPM v2.1 的云端能力应围绕一个清晰判断展开：

```text
IPM Cloud = 法律项目/案件的本地优先协作版本层
```

它不是实时网盘，不是完整 Git，也不是 AI 对话云端仓库。

推荐方向：

- 本地仍是主要工作副本；
- 用户显式提交与拉取；
- 云端保存文件对象、manifest、项目元数据、成员权限和必要协作事件；
- KnowClaw 对话和工具过程默认留在本地；
- 文件冲突以“自动保留双方版本”为主；
- 版本控制采用 hash 去重 + manifest 快照 + 大文件保留策略；
- 企业能力通过策略下发、Skill 分发和权限审计逐步增强；
- 飞书/微盘/NAS 通过 Connector Adapter 接入，不与核心同步模型耦合。

这个路线可以在保护隐私与控制存储成本的前提下，把 v2 已经完成的本地 Agent 工作流扩展到团队协作与企业交付场景。
